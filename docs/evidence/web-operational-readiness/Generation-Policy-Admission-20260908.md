## Final behavior and authority

- New catalogue requests resolve an exact existing ID or slug. Domain, structure, advice boundary, section requirements, descriptions and required facts come from the existing catalogue JSON assets. Caller-supplied hints do not replace those rules. Unknown catalogue IDs require explicit bespoke intent; a known catalogue template cannot switch to the bespoke route to replace its policy.
- Section selection is a bounded scope request. Canonical keys, selected order and deliberate stored labels are preserved. The one compatibility mapping accepts an exact catalogue heading with the exact existing request normalization; it performs no approximate title search. The pipeline receives canonical keys so its existing required-information lookup remains effective. Draft/final/missing-information/placeholder section keys are mapped back to the captured wire destination before settlement. Existing sibling prose is never remapped.
- Explicit bespoke requests retain the existing server designer. The server-created structure and cautious policy govern generation. A failed/null design now fails explicitly and releases ordinary failed admission; it cannot fall through to the caller scaffold.
- Completed results are read from the existing private allowance receipt before current catalogue restrictions. The read is bound to authenticated owner, request ID, route and the original request-body digest. A missing or malformed read fails closed. A historical settled result is replayed exactly without acquiring another allowance or provider claim.
- New execution policy version `legacy-template-policy.1` and its exact policy digest are bound to the existing allowance reservation before provider authority is issued. The policy survives released/expired attempts for the same accepted request. A later canonical retry uses its persisted policy, so an interrupted phase-2 request is not incorrectly compared with the old generic template name.
- Legacy unsettled requests with existing work require equal old/new template-policy digests before adoption. The historical stub resolver is retained only for that comparison. A changed policy produces an explicit recovery response while preserving old rows, usage and results. An active old execution claim cannot be relabelled before it expires and rotates. The old API cannot reacquire a non-settled policy-bound request.
- The new RPC response parsers validate closed shapes, exact echoed identities, policy pairing, claim tokens and durable response contracts. New read/policy-reserve inputs are copied before hashing, and cancellation is carried through the actual SDK transport. Existing `infinity` expiry values remain literal: both reconciliation holds and prepared-but-undispatched recovery can legitimately use them.
